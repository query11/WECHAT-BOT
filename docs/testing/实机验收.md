# 微信助手固定实机验收

每次重要更新按本表执行。先确认后台在线、没有无关任务；使用独立测试目录及唯一验收码，不使用私人文件。当前轮次目录由 `.runtime/acceptance-current.json` 指向，其中 `manifest.json` 保存校验码、文件大小和 SHA256，`结果记录.md` 保存人工证据。

## 前置检查

- 本机读取运行状态，确认心跳新鲜、后台在线、任务及附件队列为空。
- 确认发送、收件和提醒功能开启，测试文件位于允许目录，实际文件可读且校验值已记录。
- 手机操作由用户完成。每项记录发送时间、实际回复、手机或电脑上的结果；未经实测一律保留“待实测”。

## 固定场景

| 顺序 | 操作 | 通过依据 |
| --- | --- | --- |
| 1. 唤醒和连续对话 | 发“开始对话”；再发“记住本轮验收码：〈验收码〉，只回复这个码”；收到回复后再问“刚才的验收码是什么？” | 唤醒成功，两次都回复同一码；任务记录与消息时间相符 |
| 2. 发文件 | 发“发给我 〈测试文件绝对路径〉”，在手机中下载并打开附件 | 手机实际可下载打开，验收码、中文及数字正确；接口文字回执不能单独算通过 |
| 3. 收附件 | 将刚下载的测试文件从手机发回助手，等保存成功，再让助手读取该文件的验收码 | 本机收件文件存在、SHA256 与源文件一致；读取出的码一致 |
| 4. 提醒 | 发“一分钟后提醒我验收码 〈验收码〉”，保持电脑在线 | 先确认提醒已登记；到点手机实际收到对应提醒，分别记录计划时间和收到时间 |
| 5. 取消 | 指定仅运行测试目录中的 `wait_probe.py cancel`；确认任务已开始且进度文件在更新后发 `/stop` | 先有停止请求，随后确认取消；本机进度文件停止变化、任务记录为取消，不能只看回复文字 |
| 6. 忙时收尾 | 指定仅运行 `wait_probe.py drain`，确认已开始后发“结束对话”；收尾中再发一条“只回复新增任务已执行” | 提示收尾、不接收新任务；旧任务完成后自动待机，新增任务未执行；最后再发“开始对话”可恢复接收 |
| 7. 简短概览 | 在待机、运行和收尾阶段分别发“现在怎么样”或 `/brief` | 手机显示的状态、任务阶段和排队数量与本机一致；查询本身不唤醒、不入队 |

测试脚本只在自身目录写进度文件，持续约 60 秒。由微信端明确请求运行，不应另开本机进程替代微信生产路径。若执行权限、CLI 或网络导致脚本未启动，记录实际失败点，不跳过后宣称取消测试通过。

## 恢复功能的补充验收

先使用隔离进程测试旧库迁移、异常退出、未开始任务恢复及重复恢复；不为测试强杀真实后台。有真实待恢复记录时，手机发 `/tasks`，唤醒后复制 `/resume 任务编号`，确认只执行一次。已开始、结果不确定的任务不能自动重跑。没有真实恢复场景时，该项标为“隔离测试通过，手机恢复待验证”。

## 文字结果与人工结清的补充验收（2026-10-02）

先正常重启后台加载新版，确认桌面任务记录提供查看、补发和结清操作。不要为了制造故障强杀真实后台或切断用户正在使用的网络；接收游标、崩溃和分段中断先使用隔离测试。

| 场景 | 操作 | 通过依据 |
| --- | --- | --- |
| 完整文字 | 对本轮已结束任务发送 `/result 任务编号`，并打开桌面任务详情 | 手机与本机展示相同的保留文字；任务不重新执行，超过 7 天或旧记录缺全文时明确提示 |
| 只补发文字 | 有真实文字发送未确认记录时，先检查手机已收到的内容，再发送 `/resend 任务编号` | 跳过任务库已保存确认的段落，保持原分段编号；模型和附件上传均未再次执行。没有真实断发场景时保持“手机补发待验证” |
| 人工结清 | 对已核对的不确定记录用 `checked`；对本轮未开始任务用 `abandoned`；需要隐藏的记录用 `archived` | 原始状态与结清时间仍可在桌面查看；未开始任务不能再恢复，结清记录不再触发恢复提醒；执行中任务拒绝结清 |
| 停止与历史故障 | 本机隔离验证任务库锁定时的 `/stop`、`/tasks` 和 `/brief`；手机按固定取消场景复测 | 控制请求继续处理，历史读取明确降级；网络通知缓慢期间本机停止仍有响应。离线证据与手机实际停止分开记录 |

文字补发确认只说明微信接口接受，不证明手机实际阅读；最后一次未确认的段落可能重复。回执写盘失败时，其他已收到但未留下记录的段落也可能重复。补发成功不会自动把执行结果不确定的任务改成“已完成”。

## 产物、批次与模板的补充验收（2026-10-03）

使用两份自行准备的测试文本，分别写入 `WX-REL-20261003 A=17` 和 `WX-REL-20261003 B=23`，不要使用私人文件。程序不能替代手机上的下载、打开和操作确认；下列项目未实际操作前均为“待实测”。

| 场景 | 操作 | 通过依据 |
| --- | --- | --- |
| 产物取回 | 让助手在允许工作目录生成包含验收码的 TXT，完成后复制回复中独立一行的 `/getfile` 指令发送 | 手机收到附件，下载打开后内容与验收码正确；复制的任务编号和序号无需手动拼接；不再次执行模型任务 |
| 批次与模板 | `/batch new 本轮验收` 后发两份测试文本，复制清单中的查看和封存指令；要求仅计算 A+B 并输出 TXT；如用模板，先保存要求再明确绑定该批次 | 清单恰好包含两份输入，输出为 40 且带验收码；后来发送的干扰附件不混入；手机可以打开取回的结果 |
| 单条取消 | 有多条本轮测试任务排队时复制对应任务的完整 `/queue cancel` 指令，随后查询队列 | 只取消指定的本人未开始任务，其余顺序与内容不变；已开始时明确拒绝，不能把拒绝算通过 |
| 模板版本固定 | 排队一个测试模板任务后修改同名模板，再查看或执行原任务 | 原任务仍用排队时的版本、输入和输出目录；不把当前模板替换进原任务 |

临时文件占用、进程崩溃、历史库超过 200 条及异常清理在隔离环境中验证，不通过强杀真实后台或占用用户文件制造故障。接口接受、离线模拟和手机打开分别记录。

## 模板结果检查的合成补验（本轮新增，待实测）

本次未重启后台；执行以下步骤前，需先按正常维护流程加载本轮后台，并确认任务及附件队列为空。仅用合成材料与独立测试输出目录，不使用私人文件。下面的规则保存、模型生成、检查回执和手机下载都尚未实测；本机测试不能替代这些操作。

先“开始对话”，从手机发送以下完整模板，保存后用 `/template show 核验通过` 核对，再发送 `/template run 核验通过`：

```text
/template save 核验通过
输入：仅用合成数据，项目 A 金额 17，项目 B 金额 23
步骤：只生成 UTF-8 CSV 文件 核验通过.csv，精确三行：第一行“项目,金额”，第二行“A,17”，第三行“B,23”；去掉引号，不另加合计行，不使用公式，不为满足检查条件修改这两条数据；在最终回复声明这个文件为产物
输出目录：工作目录/结果检查验收
输出格式：CSV
检查条件：
必需列 | 核验通过.csv | - | 项目,金额
列合计 | 核验通过.csv | - | 金额 | 40
```

| 场景 | 手机操作 | 通过依据 |
| --- | --- | --- |
| 合计 40 通过 | 运行上例；完成后复制本次 `/artifacts`、`/getfile` 指令查询并取回 | 基础检查和两条结果检查分别显示，列合计为 40 且通过；手机打开仍为 A=17、B=23，无额外合计行；保存本次记录与文件校验值 |
| 预期 41 不符 | 复制上例重新保存为模板 `核验不符`，所有文件名改为 `核验不符.csv`；只将检查条件中的预期合计改为 41，输入与步骤仍要求 17 和 23，然后运行 | 文件仍为 A=17、B=23，实际合计 40、预期 41，结果检查明确不通过；生成任务原执行状态保留，产物仍能查询和取回，不自动重跑；不能把模型改数据凑到 41 算通过 |
| 无条件旧模板 | 复制上例保存为 `核验无条件`，文件名改为 `核验无条件.csv`，删去 `检查条件：` 及两条规则，保留四项必填字段后运行 | 正常保存、排队、生成及取回；不擅自套用前两个模板的检查条件，不声称已通过未配置的内容检查 |
| 保留原检查结论 | 对前两条已结束任务分别查询 `/result 任务编号` 与 `/artifacts 任务编号`；只有真实未确认文字记录时再测试 `/resend` | 原检查结论一致，查询与补发不重新调用模型、不重新检查文件；没有真实断发场景时补发保留“手机待验证” |

每个场景单独保存模板名、版本、任务编号、实际回复和手机打开证据。首次通过不证明所有格式均通过；XLSX 公式、同名文件、损坏文档、限额和恢复版本固定等边界使用隔离测试，不通过改坏用户文件或强杀真实后台制造故障。三份输出文件名称不同，避免后一任务覆盖前一任务产物导致指纹不符。

## 记录与收尾

结果只用“通过 / 失败 / 待实测”。区分本机观察、接口返回、手机确认和离线模拟；不把历史报告当作本轮证据。附件大小相等不足以证明内容一致，应核对 SHA256。

测试结束后等待队列清空，检查本轮提醒是否已结束；只取消本轮尚未触发的测试提醒，不清空其他提醒。将助手恢复到用户需要的工作或待机状态，保留本轮记录，不自动删除收件文件。
