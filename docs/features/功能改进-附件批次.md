# 附件批次：固定输入清单后再处理

异常退出后的副本回收：新建输入副本与发送快照会保存任务及运行归属，使用期间持有跨进程占用锁。后台启动时有界检查明确登记的目录，只回收未被活动任务占用、登记与内部标记一致的受管文件；不扫描工作目录，不删除原附件或产物。清理失败保留登记供后续重试。旧版未登记的残留、标记损坏或含未知文件的目录不会自动删除，需人工核对。

把多张图片、文档和一个模板明确组成同一批输入，确认清单后再交给模型处理。后收到的附件不会混入已经确认的批次；运行中心继续沿用现有布局，从微信使用批次指令。

## 新收附件组成一批

也可通过连续对话完成：“开始收集附件” → 发送附件 → “发完了，任务要求” → 核对清单后“确认执行这批附件”。确认有效期为 15 分钟，清单变化需重新核对；详见 [附件对话与桌面任务操作](功能改进-任务操作简化.md)。

先说“开始对话”，再按以下顺序操作：

1. 发 `/batch new 本次报销`，开始收集随后发送的附件，保存回复中的批次编号。
2. 发送发票图片、材料和模板。这些附件只接收并保存，附带正文不自动触发分析。
3. 接收完成后发 `/batch show 完整编号`，核对本批文件的序号与清单。
4. 若第 4 个文件是模板，发 `/batch template 完整编号 4`；不需要模板时可跳过。
5. 发 `/batch seal 完整编号`，确认输入清单固定。
6. 发 `/batch run 完整编号 按模板将三张发票整理为报销表`，才开始排队执行这批任务。

任务说明写在 `run` 后面。收集附件时随消息附带的“请分析”等文字不会提前执行，避免尚未发齐文件就开始工作。批次编号需要完整复制，不按名称或“刚才那批”猜测。

每位用户最多同时有一个正在收集的批次；开始另一批前先确认或取消上一批。确认时每批需有 1 至 12 个文件，单个不超过 20 MB，总量不超过 100 MB。批次名称为 1 至 80 个字。

## 已经保存的附件组成一批

附件已经按原流程保存时，可以发 `/batch recent 4 本次报销`。收到指令时会固定本人最新的 4 个收件登记项，从新到旧排序，再在附件后台队列中核对文件、准备清单；准备期间不能 `seal`。只选择已登记保存的附件，不包含仍在下载、下载失败或其他用户的文件。选中的某一项消失或无效时整批准备失败，不会跳过它换成更早的文件。

`recent` 建立的是选定附件批次，随后新收到的附件不会追加进来；它仍占用本人唯一的未确认批次名额。准备完成后会发送清单，必须先核对再 `seal`。`new` 则收集之后发送的附件，两种入口不要混用。

随后用 `show` 核对实际清单及序号，标记模板，再 `seal` 和 `run`。请先核对最近附件是否确实属于同一件事，数量相同不代表资料对应正确。建立批次不会重新下载附件，也不会撤销之前按普通附件流程已经进行的分析。

## 完整指令

| 指令 | 用途 |
| --- | --- |
| `/batch new 名称` | 开始收集随后发送的附件，仅保存，不自动分析 |
| `/batch recent N 名称` | 用本人已保存的最近 N 个附件建立新清单 |
| `/batch list` | 查看自己的批次列表与编号 |
| `/batch show 完整编号` | 核对指定批次的文件序号、清单和状态 |
| `/batch help` | 查看批次指令用法 |
| `/batch template 完整编号 N` | 将清单中一个文件标为模板；N 为 0 时清除标记 |
| `/batch remove 完整编号 N` | 从未确认清单移出第 N 个附件，磁盘文件保留 |
| `/batch dismiss 完整编号 失败记录编号` | 补传并核对后移除对应失败提示，保留失败接收证据 |
| `/batch seal 完整编号` | 确认清单固定，成功后进入可执行状态 |
| `/batch run 完整编号 任务说明` | 用已确认的清单绑定一条模型任务并排队 |
| `/batch cancel 完整编号` | 取消尚未使用的批次 |

指令不用带 `/cc`，但收集、确认、标模板、取消和执行需先“开始对话”；`help`、`list`、`show` 等查询在待机也可用。只能管理本人的批次。每批只标记一个模板，模板仍是输入清单的一员；设置标记不代表助手已确认其格式或业务用途。模板需在 `seal` 前标记，清单确认后不能再改；选错时取消未使用的批次并重新建立。

批次依赖启用的任务记录库 `task_journal_file`。关闭记录时不能查询、收集或执行批次，原有普通附件接收规则保持不变。批次指令需单独发送，不能在同一条指令中附带附件。

只有清单确认成功、处于可执行状态的批次才能 `run`；同一批次只绑定一次任务，不可反复运行同一批次来重复处理。想再次处理时，应另建批次并重新核对清单。

## 接收失败与清单确认

有待下载或下载失败的附件时，`seal` 不会成功。待下载先等接收完成；新收附件批次可以补传缺失文件，核对后用清单附带的 `dismiss` 指令移除对应失败记录，成功附件保留。也可明确放弃缺失项后移除失败记录，再核对实际输入清单。已经确认的批次不能修改。`recent` 准备失败仍需核对后取消并重建，不自动换用其他文件。重启时未完成的下载会记为中断失败，不会自动续接。

`cancel` 只取消未使用的批次，不删除已经保存的原附件，也不回滚先前分析。一旦绑定执行任务，停止或单条取消应使用原来的 `/stop`、`/queue cancel 任务编号` 等任务管理入口，不能用批次取消假装撤销已发生的处理。

`/queue cancel` 取消批次任务后，不会把已绑定批次重新释放为可运行状态；需要再处理时另建批次，原编号不能重复 `run`。已进入执行的任务失败或被停止后，先核对实际结果和可能已有的文件改动，再决定是否建立新批次。

## 执行时的输入版本

执行前会核对清单中所有文件的路径、大小、修改时间和 SHA-256 指纹并创建副本，将固定的文件清单和模板身份交给模型。任何文件消失、不可读或指纹变化都会拒绝整批，不会先把部分输入交给模型；需要检查源文件后重建批次。文件指纹核对只证明读取版本与登记版本一致，不证明附件内容正确，也不证明模型结果符合业务要求。

后收到的附件不会追加到本次任务。模型使用执行时创建的输入副本，原附件之后改变不会悄悄替换已经交给任务的输入版本。清单约束用于固定本任务的输入，不改变现有模型权限或文件访问范围。

临时输入副本在任务结束后清理，不能当作长期结果文件或任务产物交付。处理结果应另存到正常工作目录中的长期文件，再按产物规则登记。

批次任务异常重启后的 `/resume 任务编号` 仍按原来的“确认未开始才可手动恢复”规则执行，并保留原批次清单，不从新的最近附件重新选择输入。所有任务都不会自动重跑；已经开始的任务先检查实际结果，不直接恢复重放。

桌面任务历史详情显示该任务保存的固定输入清单，包括文件序号、名称、路径与模板身份，便于核对；沿用现有详情区，不改变运行中心布局。显示的原路径是本地定位信息，不会触发执行或自动恢复。

文件输出仍通过 [任务产物与单条队列管理](功能改进-产物与队列.md) 的 `/artifacts`、`/getfile` 查看和取回；`/result`、`/resend` 仍分别用于结果文字与未确认文字补发。

验证范围和实际运行状态见 [可靠性检查与验收](../testing/可靠性检查与验收.md)。新增对话与补救操作的验证、后台加载情况以该文档顶部为准。
