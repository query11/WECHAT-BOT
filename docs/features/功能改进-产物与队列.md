# 任务产物取回与单条队列管理

本轮沿用现有运行中心布局，新增功能通过微信指令使用。`/result` 查看结果文字、`/resend` 补发未确认文字的行为保持不变；取回文件使用下面的产物指令。

## 查看和取回任务产物

| 指令 | 用途 |
| --- | --- |
| `/artifacts 任务编号` | 查看自己的指定任务产物清单、基础检查及已配置的结果检查结论 |
| `/artifacts latest` | 查看自己最近已结束、未归档任务的产物清单 |
| `/getfile 任务编号 1` | 按清单序号取回第 1 个文件 |
| `/getfile 任务编号 all` | 请求取回清单中的全部文件 |

`/getfile` 的任务编号也可写 `latest`。任务编号可从 `/tasks`、桌面任务记录或产物清单复制；查看清单后，建议按具体任务编号取回，避免后续任务结束后 `latest` 指向另一条记录。`latest` 不会跳过没有声明的最近任务去猜测更早的产物。

三个中文说法只认完整句：

- “查看刚才的产物”对应 `/artifacts latest`。
- “把刚才的产物发给我”对应 `/getfile latest all`。
- “把刚才生成的文件发给我”对应 `/getfile latest all`。

这些指令不用带 `/cc`。清单查询在待机时也可用；取回文件属于新的附件发送任务，需先说“开始对话”，待机或收尾期间会明确拒绝，之后不会自动补做。指令需单独发送，附带图片或文件时不接收该条附件。只能查看、取回自己的已结束任务，执行中、等待确认和可恢复的未开始任务暂不能取产物。任务记录关闭或清单保存失败时，不能按任务编号取回，请保留本机路径。

## 清单的依据与检查范围

模型在最终回复中为交付文件写一条独立声明，例如：

```text
[[产物]]{"path":"D:/工作目录/结果.xlsx","label":"汇总表"}
```

每个文件独占一行；`path` 必须是绝对路径，`label` 是简短说明，JSON 中的反斜杠必须转义。桥只对明确声明的文件登记和检查，不从普通文字中出现的路径推断产物，也不会为取回文件重新执行原任务。声明本身不发送附件；用户明确要求发送时，原有发文件流程仍可使用。

登记时核对真实文件是否存在、非空、可读取，并保存路径、大小、修改时间与 SHA-256 内容指纹。每次最多核验 20 个声明，每个文件核验上限为 100 MB；超过上限或未通过检查会说明原因。检查沿用允许的文件目录范围，不登记凭据、助手配置、固定记忆或运行数据，也拒绝符号链接和 Windows junction 等路径重定向。

基础检查范围随文件类型不同：

- 文本检查可解码读取；JSON、XML 检查能否解析。
- DOCX、XLSX、PPTX 检查 ZIP 包能否有界读取、成员完整性及核心 XML 包结构；不检查段落、表格、公式或幻灯片内容是否正确，也不证明 Office 能完整打开。
- PDF 检查文件头与结束标记；常见图片检查基础文件头、尺寸或结束结构。两类均不做完整页面渲染或图像解码。
- 未知格式只检查存在、非空和基础读取，清单明确显示“基础读取通过（未核验格式）”。

这些证据不证明文件内容正确、文件由本任务创建、手机能打开，也不证明模型已经完成全部要求。失败声明会列出原因，不能按任务直接发送。

模板可另行配置必需列、列合计或必需章节，语法与范围见 [任务模板的结果检查](功能改进-任务模板.md)。这层结果检查与上述基础核验分别显示，只检查明示条件，不做语义审核。结果检查不通过或未能检查时，文件仍保留；通过基础核验且满足原发送规则的产物仍可取回，不自动重跑或改写生成任务执行终态。`/result`、`/resend` 保留原回执结论，不重新运行检查。本轮新增结果检查需后台加载后生效，当前测试与加载状态见 [可靠性检查与验收](../testing/可靠性检查与验收.md)。

## 发送时再次核对版本

取回沿用原发送配置：默认每次最多 3 个文件、单个不超过 20 MB，由 `send_file.max_per_reply`、`send_file.max_mb` 控制。核验能接受的 100 MB 文件不一定可以发送。`all` 超过单次文件数量上限时，整次请求不会先发一部分，会要求按清单序号分别取回；选中的文件必须全部通过原始检查及发送范围、大小检查。

真正上传前会重新读取文件并核对登记时的指纹。文件改变、消失或不可读时拒绝上传，不会悄悄改发新版本。核对通过后上传内部临时快照，保证发送的是该指纹对应的文件字节；快照存放位置不扩大原来源文件的访问范围。旧任务的记录仍保留原版本信息。

发送成功回执表示微信接口已接受，不代表手机已下载或阅读。未获得确认时先查看手机附件，避免重复发送。`/resend` 仍只补发文字，不会重新上传产物；需要文件时使用 `/getfile`。

上传结果与临时快照清理结果分别记录。上传已获接口确认后，即使本地快照被占用、暂时清理失败，也保留原发送回执，不改报“读文件失败”。清理问题写入本机日志，受管快照留待后续回收，不因此自动重传文件。

产物清单为通过检查的每个文件分别附上带完整任务编号和原序号的取回指令，一行一条，可直接复制。清单未成功保存时不提供不能使用的取回指令。

## 单条取消、修改和调序

先发 `/queue`，复制对应的完整 32 位任务编号。清单显示全机队列位置及“你的第 N 条”；其他用户的任务内容和编号不展示。

| 指令 | 用途 |
| --- | --- |
| `/queue cancel 完整编号` | 取消自己尚未开始的一条任务 |
| `/queue edit 完整编号 新正文` | 修改自己尚未开始的普通文字任务正文 |
| `/queue move 完整编号 N` | 调到本人等待任务中的第 N 条，从 1 开始 |

单条操作只接受完整稳定编号，不用“第三件事”或短编号猜测。只能操作本人尚未领取执行的任务；已经开始或收到停止请求的任务会拒绝单条操作。普通文字任务可以修改、取消和调序；带附件、点击、截图或发文件任务只能取消或调序。

`edit` 保留新正文的大小写与换行，开始执行时交给原模型任务通道；它不会立即执行新正文里的管理动作。例如改成“关机”只是改了等待执行的模型正文，不会立即进入桥的关机通道。保存任务记录失败时保留原任务及原正文，不报告修改或取消成功。

`move` 的 N 是本人序号，其他用户占据的队列位置不变。队列继续全局串行，修改或核验任务记录期间不会让后续任务越过前面的任务。调序仅影响本次运行中的内存顺序，不保存跨重启的执行顺序。

收尾期间可以查看队列并执行这些单条管理指令，不需要重新唤醒；新的普通任务或文件取回仍需先“开始对话”。`/queue clear` 保持原来的全机清空语义；`/stop` 停当前任务，`/stopall` 还取消当时排队的任务。

启用任务记录时，修改后的尚未开始普通文字任务正文可在异常重启后通过 `/tasks` 中的 `/resume` 手动恢复；已取消任务不恢复，所有任务都不会自动重跑。关闭任务记录后，单条队列操作仍可用，但编号仅在本次运行中有效，没有持久化记录或跨重启恢复。

验证范围和实际运行状态以 [可靠性检查与验收](../testing/可靠性检查与验收.md) 为准。本轮后台已正常重启加载；手机取回及手机打开文件仍待实机验收。
